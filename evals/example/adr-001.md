# ADR-001: Delegate bank credentials to a third-party aggregator rather than holding them

## Status

Accepted

## Context

The system replaces a by-hand accounting process and must retrieve
transactions from the user's financial institutions automatically. Four
constraints were in force and in tension with each other:

- **Zero recurring cost** across the whole system, not merely the AI
  portion.
- **Automatic retrieval**, not files the user downloads by hand.
- **Reachable as a hosted web app** from any device, which raises rather
  than lowers the security bar.
- **A security standard defensible for money**, not for a side project.

If the system connected to institutions directly, the thing proving the
user's identity to their bank would be the highest-value asset the system
would ever hold — higher than the transaction data itself, since a defect
exposing it is not recoverable by correcting a record.

The system is single-user today but is expected to serve a partner later,
so no design may assume one permanent identity.

## Decision

A third-party aggregator holds the user's bank credentials and returns an
access token; the credentials never enter this system. **Plaid** is that
aggregator.

## Alternatives considered

**Direct connection to each institution.** Free where the institution
supports it, and involves no third party. Rejected because the system would
then hold the bank credentials itself — precisely the asset this decision
exists to keep out — and institutional support for this route is shrinking
rather than growing.

**Automating the institution's website.** Free and applicable to any
institution. Rejected on three counts: the system holds full credentials,
the integration breaks whenever the site changes, and it typically violates
the institution's terms of service.

**Teller.** Met the zero-cost bar and delegated credentials properly, and
was the better fit for the first slice specifically, since its connection
flow requires no registered callback and would have kept a local-only first
version simpler. Rejected on coverage: support for the online-only bank and
the card issuer the user named was unconfirmed, and its authoritative
coverage list is itself an authenticated endpoint requiring a client
certificate — meaning real setup work before learning whether it covers the
accounts at all.

**SimpleFIN.** The only candidate where read-only access is structural
rather than a consequence of what the application requests. Rejected on
cost: it carries an annual fee, and the user reaffirmed the zero-cost
constraint rather than reopening it when offered the trade-off explicitly.

## Consequences

**What becomes easier**

- The strongest security property available is now an absence rather than a
  practice: the bank credential is not protected carefully, it is not
  present. Absence is verifiable in a way that careful handling is not.
- Coverage spans major banks, an online-only bank, and a card issuer
  without separate integrations.
- Free at personal scale, satisfying the constraint that drove the choice.
- Credential revocation and data deletion are available to the user
  independently of this application.

**What becomes harder, and what is accepted**

- **A third party now holds the credentials and the transaction history.**
  This is an accepted risk, taken on the reasoning that an aggregator whose
  core business is protecting credentials is better resourced for it than a
  self-built application. It is a risk, not an elimination of one.
- **Read-only access is application-side discipline, not a guarantee.** It
  holds because this application requests only transaction data; the
  provider offers payment capabilities it simply does not ask for. The
  rejected alternative would have made this structural.
- **The central property holds by observed behavior, not written
  guarantee.** The vetting bar chosen was read-only access and revocation
  with deletion. A published security posture and a documented commitment
  that credentials are never returned to the connecting application were
  both offered and declined as requirements. This is recorded as a decision
  rather than an oversight, and it is worth revisiting if the system ever
  becomes reachable from the network.
- **Provider unavailability means no data.** There is no fallback retrieval
  path, and adding one would reintroduce a rejected alternative.
- **Local development is not friction-free.** Institutions using delegated
  authorization require an encrypted callback, so even a local-only version
  carries certificate setup.
- **The provider's model pushes toward a network-reachable system over
  time.** Its update and reconnection mechanisms assume an endpoint it can
  reach. The first slice deliberately avoids this and remains workable
  without it, but this decision puts a real deadline behind the hosting and
  authentication work rather than leaving it indefinitely deferrable.

**What this forecloses**

Holding bank credentials directly, and any architecture with no third party
between this system and the institutions. Switching providers later remains
possible — the integration is isolated behind a boundary for exactly this
reason — but because the choice was driven by coverage, switching means
re-verifying coverage first rather than swapping an equivalent part.
