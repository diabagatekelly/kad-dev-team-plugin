# ADR-002: Build on TypeScript and Node across server and browser

## Status

Accepted

## Context

The system is a web application maintained by one person, for their own
finances. It needs a browser interface and a server-side integration with a
financial data provider, and the server side is not optional: the provider
relationship involves a secret that cannot live in a browser.

The choice had to be scaled to a single maintainer. Tooling that a team
would absorb comfortably is tooling one person stops maintaining.

One structural fact shaped this: the system's most correctness-sensitive
seam is the translation of the provider's data into the system's own
representation of a transaction. Everything downstream — categorization,
budgets, transfer figures — is derived from that translation being right.

## Decision

TypeScript on Node, used for both the server and the browser.

## Alternatives considered

**A Python server with a JavaScript browser interface.** Strong libraries
and pleasant to work in. Rejected because the browser interface is not
optional, so this means two languages and two dependency ecosystems
maintained by one person — the cost a solo maintainer feels most and the
one most likely to result in half the system going stale.

**A Go server with a JavaScript browser interface.** A notably smaller
dependency surface, which genuinely suits a system handling financial data,
and a single deployable artifact. Rejected for the same two-ecosystem cost,
compounded by a smaller pool of provider client libraries.

## Consequences

**What becomes easier**

- One language and one ecosystem for the whole system, which is the
  difference between a solo maintainer keeping all of it current and
  keeping half of it current.
- Static typing lands where it is worth the most: at the boundary where
  external data becomes the system's own, which is the seam every later
  capability depends on.
- The provider ecosystem treats this platform as its primary target, so
  integration work follows documented paths rather than improvised ones.

**What becomes harder, and what is accepted**

- **This ecosystem carries the largest dependency surface of the options
  considered**, on a system whose stated premise is minimizing what touches
  financial data. This is a real cost and the strongest argument for the
  rejected alternatives.
- It is mitigated, not removed, by a deliberately strict dependency
  posture: exact versions, a committed lockfile covering transitive
  dependencies, installs that fail rather than drift, and third-party
  install-time scripts disabled by default. The posture was chosen at the
  same moment as the language, specifically because retrofitting it later
  across a grown dependency tree is far more expensive.
- Every added dependency is a decision with a security cost attached, not
  merely a convenience. This is a standard this project has to keep
  applying, which is a form of ongoing effort the rejected alternatives
  would have required less of.

**What this forecloses**

A single self-contained deployable artifact, and the smaller attack surface
that comes with one. Reversing this decision would mean rewriting rather
than porting, which is why it is recorded here rather than left implicit.
