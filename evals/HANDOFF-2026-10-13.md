## Who and what

`kad-dev-team` is the user's Claude Code plugin: personas (agents) plus
skills for a planning-to-delivery flow (problem framing, requirements,
vertical slicing, architecture design, tdd implementation, the review
family, devsecops), with an eval suite under `evals/` run by
`claude plugin eval` (pinned at CLI 2.1.296). The user wants the suite to
be something they can rely on as the validation layer for an autonomous
code writer.

## The direction the user chose (2026-10-12)

Settled after weighing "remove the human orchestrator entirely" against
"keep some human orchestration without bottlenecks":

- Planning stages (framing, requirements, slicing, design) stay
  human-gated. Deciding what to build is the user's job and they keep it.
- The code writer (tdd-coach, through the orchestrator's
  quarantine/grade/combine flow) is meant to be fully autonomous: never
  blocks on a question, assumes visibly, escalates in its report.
  Quarantine = two subagents implement the same slice in isolated
  worktrees; Grade = mechanical checks plus a blind pairwise judge;
  Combine = the orchestrator takes the best of each and submits.
- A vertical slice stays the unit of delivery (one PR = one slice). The
  implementer may get the whole unit (slice set, requirements, designs,
  architecture map) as read context, but does not batch slices.
- One plugin, not two: lightness is a policy switch on orchestration.
  Experiments on two repos are fine.
- Agreed fix order for the plugin itself (not started, except the first
  tool): a mechanical validation gate in front of Grade
  (`tools/validation_gate.py`, built, not yet wired into the
  orchestrator's Grade step), promote `tools/pairwise_judge.py` to the
  arbiter, full reviewer pass on the finalized build, diversify candidate
  inputs, sandbox the code-writing agent.

## Why the audit

Before trusting the suite as that validation layer, the user asked
whether it would actually catch a regression. The audit
(`AUDIT-2026-10-12.md`) found: bars were "last score seen" recorded under
calibration mode while the gate scores under a different mode; a 0.1
tolerance on the aggregate let one grader fail forever; 227 of 532
graders judged `last_message`, where the judge is noisy on long text;
three phase-3 chains were answered by their frozen history; the tdd
cases' process graders could be bypassed and were blind to Bash writes;
several prompts or fixtures pointed at the plant. `TODO.md` turns that
into phases A–G.

## Running evals: what we learned the hard way

- **Windows cannot run a case that grants Bash.** The CLI refuses a
  shell grant without a sandbox backend, and still writes a scored
  result for the refused zero-turn run; both tools treat it as an error.
  Until 2026-10-14 the gate granted Bash to every case, so no gate case
  ran on Windows; it now grants each case only the gated tools its own
  `allowed_tools` names (four cases name Bash), so the other 105 should
  run on Windows too. Not yet tried.
- **The PR check no longer runs evals (decided 2026-10-13 evening).**
  The user does not want API spend on top of the subscription, so the
  workflow's pull-request job is `eval_evidence.py`: for every case the
  diff reaches, `evals/evidence.json` must hold a passing gate run whose
  fingerprint (sha256 of every file the case loads, CRLF folded) matches
  the PR's files and whose score clears the bar. `eval_gate.py` writes
  that file for passing cases; `wsl-gate.sh` copies it back to Windows;
  `.githooks/pre-push` runs the same check before a push (enabled in
  this clone with `git config core.hooksPath .githooks`). The paid job
  survives under `workflow_dispatch` only.
  Verified end to end: a three-run named-fix gate through `wsl-gate.sh`
  took 1.3 minutes wall-clock (the runs started in the same second,
  `-j 3`), wrote the entry, and the Windows check read it as ok.
- **Parallelism**: `eval_gate.py --parallel 8` caps agent runs in flight
  across all cases; a case at N runs takes N slots and passes `-j N` to
  the CLI (max 8 per process). `--jobs 6` still caps cases. The 108-case
  `--all` at one run each is roughly 20 minutes wall-clock but about
  three five-hour subscription windows of usage; the earlier "an hour"
  estimates came from serial runs and two timeout outliers.
- **Old GitHub workflow facts, if the paid job is ever used again**:
  Ubuntu 22.04 image (24.04's AppArmor restriction on unprivileged user
  namespaces breaks bubblewrap's loopback setup; the model then quietly
  reviews with Read/Grep and tdd cases cannot run tests), a `bwrap`
  probe step before anything is spent, 300-minute job limit. Results
  upload as the `eval-results` artifact. Costs seen: about $0.45 per
  review case including the judge; the full 36-case set came to $16
