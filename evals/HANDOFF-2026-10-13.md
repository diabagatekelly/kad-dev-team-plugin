## Who and what

`kad-dev-team` is the user's Claude Code plugin: personas (agents) plus
skills for a planning-to-delivery flow (problem framing, requirements,
vertical slicing, architecture design, tdd implementation, the review
family, devsecops), with an eval suite under `evals/` run by
`claude plugin eval` (pinned at CLI 2.1.296). The user wants the suite to
be something they can rely on as the validation layer for an autonomous
code writer.

## The direction the user chose (2026-10-12)

Settled after weighing "remove the human orchestrator entirely" against
"keep some human orchestration without bottlenecks":

- Planning stages (framing, requirements, slicing, design) stay
  human-gated. Deciding what to build is the user's job and they keep it.
- The code writer (tdd-coach, through the orchestrator's
  quarantine/grade/combine flow) is meant to be fully autonomous: never
  blocks on a question, assumes visibly, escalates in its report.
  Quarantine = two subagents implement the same slice in isolated
  worktrees; Grade = mechanical checks plus a blind pairwise judge;
  Combine = the orchestrator takes the best of each and submits.
- A vertical slice stays the unit of delivery (one PR = one slice). The
  implementer may get the whole unit (slice set, requirements, designs,
  architecture map) as read context, but does not batch slices.
- One plugin, not two: lightness is a policy switch on orchestration.
  Experiments on two repos are fine.
- Agreed fix order for the plugin itself (H in `TODO.md`): a mechanical
  validation gate in front of Grade (done 2026-10-17, H1:
  `skills/orchestrator/scripts/validation_gate.py`, wired into the
  orchestrator's Grade and Finalize steps), promote
  `tools/pairwise_judge.py` to the arbiter, full reviewer pass on the
  finalized build, diversify candidate inputs, sandbox the code-writing
  agent.

## Why the audit

Before trusting the suite as that validation layer, the user asked
whether it would actually catch a regression. The audit
(`AUDIT-2026-10-12.md`) found: bars were "last score seen" recorded under
calibration mode while the gate scores under a different mode; a 0.1
tolerance on the aggregate let one grader fail forever; 227 of 532
graders judged `last_message`, where the judge is noisy on long text;
three phase-3 chains were answered by their frozen history; the tdd
cases' process graders could be bypassed and were blind to Bash writes;
several prompts or fixtures pointed at the plant. `TODO.md` turns that
into phases A–G.

## Running evals: what we learned the hard way

- **Windows cannot run a case that grants Bash.** The CLI refuses a
  shell grant without a sandbox backend, and still writes a scored
  result for the refused zero-turn run; both tools treat it as an error.
  Until 2026-10-14 the gate granted Bash to every case, so no gate case
  ran on Windows; it now grants each case only the gated tools its own
  `allowed_tools` names (four cases name Bash), so the other 105 should
  run on Windows too. Not yet tried.
- **A script under a skill directory is part of that skill's evidence
  hash** (learned 2026-10-17 on H1). `affected_cases.py` maps any file
  under `skills/<s>/` to the cases tagged `<s>`, so editing
  `skills/orchestrator/scripts/validation_gate.py` after a run has
  started stales every orchestrator case, even though no eval runs the
  script. Finish the script, then launch the run. The same holds for
  `scripts/pairwise_judge.py` since H2 moved it there, and for a
  comment: H2's `nosemgrep` marker alone cost a third 48-run batch. A run cut by
  the WSL session limit leaves the unfinished cases with **no
  evidence** (their failed run overwrites the entry), not "stale", so
  `--stale` does not pick them up; list them from `eval_evidence.py`'s
  "no evidence" rows and pass them as `--cases`. The limit reset about
  two hours after it hit (at roughly 150 runs from the first batch).
  Results files: `cases[0].arms.with` is the list of runs, each run's
  `graders[]` carries `passed`, `explanation` (the judge votes) and
  `evidence` (the judged text); print with utf-8 stdout on Windows.
- **Sourcery's security findings block its check until the line says
  otherwise** (learned 2026-10-17 on PR #10). Its opengrep rule
  `python.lang.security.audit.dangerous-subprocess-use-audit` fires on
  any `subprocess.run` whose argument list is not all literals, and the
  "Sourcery review" check stays red while such a thread is open. Replying
  with the reason and resolving the thread did not clear it; a
  `# nosemgrep: <rule id>` comment on the call did (PR #9 had done the
  same on the gate's test-runner call). Decline on the merits in
  `TODO.md`, put the marker on the line, and expect the marker to re-run
  the skill's cases since it changes a file under `skills/`. Sourcery
  also auto-resolves the threads a later commit fixes, so the open ones
  after a push are the real remainder.
- **The PR check no longer runs evals (decided 2026-10-13 evening).**
  The user does not want API spend on top of the subscription, so the
  workflow's pull-request job is `eval_evidence.py`: for every case the
  diff reaches, `evals/evidence.json` must hold a passing gate run whose
  fingerprint (sha256 of every file the case loads, CRLF folded) matches
  the PR's files and whose score clears the bar. `eval_gate.py` writes
  that file for passing cases; `wsl-gate.sh` copies it back to Windows;
  `.githooks/pre-push` runs the same check before a push (enabled in
  this clone with `git config core.hooksPath .githooks`). The paid job
  survives under `workflow_dispatch` only.
  Verified end to end: a three-run named-fix gate through `wsl-gate.sh`
  took 1.3 minutes wall-clock (the runs started in the same second,
  `-j 3`), wrote the entry, and the Windows check read it as ok.
- **Parallelism**: `eval_gate.py --parallel 8` caps agent runs in flight
  across all cases; a case at N runs takes N slots and passes `-j N` to
  the CLI (max 8 per process). `--jobs 6` still caps cases. The 108-case
  `--all` at one run each is roughly 20 minutes wall-clock but about
  three five-hour subscription windows of usage; the earlier "an hour"
  estimates came from serial runs and two timeout outliers.

- **Two lessons from phase F, 2026-10-15, worth knowing before editing a
  skill or a rubric:**
  1. A skill rule that lives only in the reply ("your response opens
     with...") is skipped by Sonnet when the user hands over a finished
     case: nine runs in nine, under two wordings. The same rule held
     every time once the template carried it, because the model writing
     the file writes the template. Put a must-happen step into the
     artifact's template, not only into the instructions.
  2. A judge that fails a correct output 3-0 and, asked to explain with
     `rejudge.py --explain`, corrects itself to PASS is tripping on the
     rubric's wording, not the output. Reword what counts; a re-run
     changes nothing.
- **Two lessons from phase G, 2026-10-17:**
  1. On a one-word judge, a rubric that grows a clause for every false
     failure gets noisier, not stricter: the stop cases' scope-menu
     grader went 0.58 → 0.67 → 0.58 across three rewordings that each
     added an allowance, and 3/3 once it was cut to "FAIL only for these
     two things; everything else passes", with the allowances listed
     after the FAIL clause as examples. `rejudge.py --criteria-from`
     against the recorded outputs (`--votes 3`) shows the effect of a
     rewording before a run is spent.
  2. A grader that pins content from a frozen history (the phase-3
     `decisions-all-approved` forks) fails 3/3 the moment the history is
     re-frozen, however correct the new output; its own text says to
     re-pin, and the re-freeze checklist should include reading every
     grader of every later phase for pins. The design-system phase-3
     scaffold already fails loudly on a stale pin; the requirements
     phase-3 cases do not, and did not.
  3. A skill edit re-freezes every chain that embeds the skill, and phase
     G edited the two requirements skills twice (the stop template, then
     one line in it), so both chains were re-frozen twice in a day,
     about forty runs each time. Before re-freezing, read the skill once
     more for anything else the runs have shown, and batch the edits.
  4. A fixture copied into a different context lies: the cancel-hold
     design plant says "existing port" because it was written for the
     library app, and in the empty-repo tech-bootstrap case two runs in
     three stopped to ask about the contradiction. A scaffold that
     rewrites the words for its context (and fails if the old ones
     survive) is the fix; `grep -l` the plant across `evals/*/scaffold.sh`
     before changing the plant itself.
- **Mechanics from phase F**: driving WSL from the Bash tool: `wsl -- bash -c
  '...'` has its `$(...)` expanded by the outer shell before WSL sees it,
  so write the script to the scratchpad, strip CRLF with
  `wsl -- sed -i 's/\r$//' file`, and run `wsl -- bash /mnt/c/...`.
  `rejudge.py` sends its prompt as utf-8 now (it crashed on `→` in a
  judged file). A resumed phase's transcript sits next to the clone's
  `history.jsonl` as `<session-id>.jsonl`; name it explicitly.
  `record_thresholds.py` on 64 cases changed no fingerprint this time.
  Five batches of 78, 57, 15, 9 and 105 runs: the session limit hit at
  about 160 runs from the first batch's start and the reset was two
  and a half hours later, not five.
- **Real misses the traces showed** (both fixed in the skill, both
  verified by re-runs): Sonnet writes source through `cat >` heredocs,
  `sed -i` and Python one-liners unless told which tools to use, which
  blinds every Write/Edit ordering grader; and after the can-it-fail
  flip it restores the code and narrates "green again" without a run.
  The model also calls Write with a `path` key sometimes, which the CLI
  accepts; graders now match either key.
