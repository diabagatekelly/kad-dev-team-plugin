# Eval suite audit — 2026-10-12

Question asked: is this a suite of evals that can be relied on? Lens agreed
beforehand: process versus outcome, grader validity, bar integrity, blind
spots, fixture leakage. Scope: all 109 cases (96 `case.yaml`, 13
`prompt.md`+`graders/`), 532 graders, `thresholds.json`, the gate tools, the
fixtures and histories each grader cites, and the skills each case targets.

Method: a mechanical inventory and gate-slack computation over every case,
four family-by-family close reads, and direct verification of every finding
listed as confirmed below. `evals/results/` is gitignored and absent on this
machine, so nothing here is based on per-grader pass data from real runs;
where the README records run behaviour it is cited.

## Verdict

The suite is a good regression guard for the review skills and a poor
measure of almost everything else. It will catch a review skill that stops
finding a planted defect. It will not reliably catch an implementer that
writes code before tests, a requirements skill that infers what it should
have asked, or an orchestrator that routes correctly and then does the
routed step badly. About a third of the score mass is process counting or
transcription, and the gate's arithmetic lets a single grader regress
permanently in 23 cases without failing.

Family tallies from the four close reads (sound / weak / broken):

| Family | Cases | Sound | Weak | Broken |
|---|---|---|---|---|
| Review skills (architecture, code, test-quality, map, why-comments, tdd) | 31 | 20 | 11 | 0 |
| DevSecOps (security, reliability, supply-chain, ops) | 38 | 25 | 10 | 3 |
| Planning and docs (orchestrator, PM, slicer, docs-writer, bootstrap, adr) | 34 | 9 | 23 | 2 |
| UI (design-system, screen-design, accessibility) | 7 | 3 | 3 | 1 |

"Broken" means the case cannot distinguish the skill from a competent
copier or an empty output. "Weak" means the main promise is graded by a
proxy a bad run can satisfy.

## 1. The gate's arithmetic

- **The bar is the last score, not a floor.** `record_thresholds.py` writes
  the most recent run's aggregate; 76 of 107 bars sit at 1.0, 39 were
  recorded from a single run. A suite at ceiling can detect regressions but
  cannot show improvement, so it cannot run the lite-versus-heavy
  experiment as it stands.
- **Tolerance is on the aggregate, so graders can vanish.** With
  `--tolerance 0.1`, a case with ten or more graders can lose one grader
  on every run and pass. 23 cases have this slack; the two tdd
  cancel-hold cases can lose 2 and 4 graders respectively. Bar 0.667 on
  `reliability-review-catalog` means that case cannot regress at all.
- **Bars and gate were scored under different rules.** Every bar's
  `source` is a calibration run, which the README runs with `--ablation
  with-without`; under that mode `tool_used: Skill` graders are unscored
  indicators (CLI help confirms). The gate runs `--ablation none`, where
  the same graders are scored and almost always pass. 78 cases carry one;
  the gate therefore scores slightly higher than the bar it compares
  against. Re-record bars from a gate-mode run, or run the gate in the
  same mode.
- **Two cases are not gated.** `architecture-review-neg-security-review`
  and `architecture-review-neg-test-quality-review` are in the old
  markdown format with no recorded bar; the gate reports them as "new"
  forever.
- **Two bars bake in a grader that can never pass.**
  `library-app-lending-review-via-agent` and
  `code-review-fine-notices-pr-via-agent` require both `tool: Agent` and
  `tool: Task` with `min: 1`; one CLI version records one name. The 0.867
  and 0.9 bars include that permanent failure, and fixing the grader would
  "raise" the score with no skill change.
- **Four phase chains resume a history older than their skill.** The
  `history.jsonl` for the reliability-requirements, security-requirements
  and supply-chain-review-accept chains was frozen on 2026-10-10; each
  skill changed on 2026-10-11. Phase 2 and 3 start from a transcript the
  current skill may no longer produce. The reliability-requirements
  histories also contain an `Agent` (Explore) call the case's own
  `allowed_tools` forbids, so phase 2 is graded on analysis the case could
  not generate.

## 2. Process versus outcome

Inventory of the 532 graders:

| Class | Count | What it proves |
|---|---|---|
| LLM judge on `last_message` | 227 | the final message, which the README records the judge mis-scoring when long |
| Process (`tool_used`, `tool_order`, trace regex, trace-focus LLM) | 185 | a tool was named, or named before another tool |
| LLM judge on a saved file | 93 | the artifact itself |
| `file_exists` | 27 | a path exists, any content |

- **27 cases have no outcome grader at all**: the 13 negative-trigger
  cases (vacuous by design, acceptable) and all 13 `orchestrator-route-*`
  cases plus `orchestrator-backward-route`. A run that invokes
  `orchestrator`, invokes the right skill, writes an empty log and stops
  scores 100% on 12 route cases. Nothing checks the log entry's content,
  the save location passed, or that the orchestrator did not answer the
  routed skill's questions itself. `orchestrator-route-slicing` recorded
  1.0 on runs that invoked a non-existent `kad-dev-team:product-slicer`
  skill.
- **Skill-call counting stands in for review.** `reviews-each-cycle` and
  `final-review-runs` in the tdd cases count `test-quality-review` and
  reviewer Skill calls; four back-to-back calls at the end satisfy them.
  Nothing checks that a Critical or High finding was fixed and the
  reviewer re-run.
- **The can-it-fail check is self-reported.**
  `reports-test-list-and-can-fail-check` passes on a sentence in the
  report saying the implementation was broken and restored. The trace
  holds the proof and is never consulted.

## 3. Transcription and leakage

Cases where the graded answer is already in the input:

- **Phase-3 chains.** `security-requirements-payfine-phase3`: the frozen
  phase-2 document in `history.jsonl` already contains the waive/refund
  rejection, the other-member rejection, "raw card number is never
  received, stored, or logged", the generic error message and the card
  token never in captured context. Four of six graders are met by
  re-emitting it. `reliability-requirements-payfine-phase3`: same shape,
  four of six. `technology-bootstrap-phase3`: all five LLM graders are
  answered by the frozen phase-2 message (pnpm's default posture, every
  rejected alternative with its reason, "deliberately left open" with the
  in-memory reason). Phase 3's prompt is "React with Vite is fine. Go
  ahead and write it up." No chain in the suite contains an answer that
  rejects the skill's recommendation, which the README's own playbook
  requires.
- **Prompts that are the skill's worked example.**
  `acceptance-criteria-payfine` asks about "The payment flow handles
  errors gracefully." `skills/acceptance-criteria/SKILL.md` line 66 works
  that exact sentence. The README records the baseline passing.
  `vertical-slicing-handback` tests the refund scenario the vertical-slicing
  skill uses as its own example, and the fixture's
  `security-requirements-001.md` pre-states "is a scope decision for
  product-slicer".
- **Prompts that point at the plant.** `security-review-reminders` ("Pay
  attention to how member data is handled"), `reliability-review-http`
  ("is anything going to fall over as data grows?"),
  `reliability-review-fine-payment` ("What happens when the payment
  provider or the database misbehaves?"), `map-query-consults` (the prompt
  states the staleness the `caveats-stale-map` grader rewards),
  `test-quality-review-fines` (prompt is the skill description's trigger
  sentence verbatim).
- **Fixtures that name the next persona.** `pay-fine-security/design-001.md`
  has a heading "Open for devsecops-engineer";
  `pay-fine-screen/.../screen-design-001.md` names `accessibility-engineer`;
  `backward-pm/slice-000.md` names requirements-refinement. The routing
  cases test reading a signpost, not inspection.
- **Phase-2 requirements as sorting.** `requirements-refinement-payfine-phase2`'s
  prompt supplies the user, the need, the trade-off with its reason, the
  rejected alternative with its reason, the four in-scope items and both
  exclusions. Four of seven LLM graders are satisfied by placing those
  under headings. The skill's headline promise, never inferring the WHAT,
  is unobservable because nothing is left to infer.
- **Graders bound to names that exist only in a frozen history.**
  `design-system-payfine-phase3`'s `chosen-direction-committed` and
  `rejected-candidates-in-prose` hardcode "Warm Civic", "Crisp Civic-Tech"
  and "Reading Room", which came from the recorded phase-2 turn. Any
  re-freeze fails both graders silently.

## 4. Vacuous floors

Score an empty or one-line output would receive:

| Case | Floor | Why |
|---|---|---|
| `library-app-catalog-review`, `security-review-catalog`, `reliability-review-catalog` | 1.0 | the only scored grader is "nothing above Low"; nothing requires naming what holds the module up |
| `accessibility-review-payfine-subtle` | 0.56 | three "does not flag" traps plus skill-invoked and file-exists |
| `accessibility-review-payfine` | 0.64 | same, plus honesty-of-method and mockup-untouched |
| `security-requirements-payfine-phase2`, `reliability-requirements-payfine-phase2` | 0.67 | two of three graders are "does not" |
| `code-review-fine-notices-pr` | ~0.5 | four of eight LLM graders are "does not" |

The fix is the same everywhere: a trap grader should pass only if the
review reports at least one real finding and none of them is the trap.

## 5. `last_message` on long reports

The README records the judge failing a long review as `last_message` while
passing identical text as a file, and via-agent runs ending on a postscript
that then gets graded instead of the report. Every LLM grader in the
devsecops families (about 60), twelve review cases in the code families and
the three tdd report graders use `last_message`. `code-review-days-left-pr`
already shows the fix: the prompt asks for `docs/reviews/days-left.md` and
the graders use `focus: {source: file}`. `reliability-review-catalog`'s
0.667 is this problem: the README records the failing run as 3/3 by the
grader's own terms, failed by the judge anyway, and the criterion has since
grown a list of prose exclusions.

## 6. The tdd-implementation cases specifically

These matter most for the direction decided this week (autonomous
implementer, human-gated planning). Findings on `tdd-implementation-cancel-hold`
and its via-agent twin, all verified:

- `queue-test-before-queue-code`: any test file written at any point before
  the queue edit passes. `use-case-test-before-use-case`: an empty test
  stub, then the code, then the real test passes.
- `stays-inside-the-slice`, `touches-only-the-fix` (named-fix) and
  `writes-only-the-map` (map-update) watch only Edit and Write. `Bash` is
  allowed, so a heredoc or `sed -i` into `main/server.ts` is invisible.
- `red-runs-seen` requires four runs containing `ℹ fail`; four runs broken
  by an import error pass, and the via-agent case fails it on every run
  by construction (README line 279) because the subagent repeats fewer
  red runs. "Fails for the right reason" is never checked.
- `last-test-run-green` is `not_contains` on a trailing failure, so it
  passes when no summary line reaches the trace at all. `named-fix` has
  the positive `a-green-run-happened` grader; the two cancel-hold cases
  do not.
- `design-doc-ends-unchanged` anchors only from `## Decisions` to the end
  of file. An answer written into "Structure" or "Boundaries" passes, and
  the README records exactly that edit on the agent path.
- Every RED/GREEN regex depends on Node's spec reporter glyph. The
  fixture's test script sets no `--test-reporter`; a runtime that picks
  TAP when piped would flip these silently.
- Nothing grades coverage, mutation, the REFACTOR step, the full-suite run
  after GREEN, the `map-query` consult before implementation (it happens,
  per `skills_invoked`, but is ungraded), or the quarantine flow.
- `escalates-queue-question` accepts "product, or the user" as the owner;
  the skill requires naming `architecture-design` or `acceptance-criteria`.

## 7. Outright bugs

- `orchestrator-asks-for-target/does-not-search-for-artifacts`: the
  single-quoted YAML `'\\.md|docs|…'` is the regex `\\.md`, a literal
  backslash. A `**/*.md` glob escapes it. Only `Glob` is checked, not
  `Grep`.
- `map-update-cancel-hold/writes-only-the-map`: keyed to `/home/cwd/`; an
  absolute path under any other run directory never matches, so every
  write passes.
- `security-review-portal-pr/finds-member-profile-idor` fails a review that
  says "missing authentication" for what is an authorization gap; three
  other devsecops graders require one specific fix with no "or
  equivalent".
- `technology-bootstrap-*` criteria say "This is a NEGATIVE grader" and
  "Score 0 / Score 1" to a PASS/FAIL judge; the phase-3 copy grades a file
  with "must NOT ask the user", which a saved file never does.
- `accessibility-review-payfine-subtle` lacks `leaves-the-mockup-alone`,
  `says-it-read-the-markup` and `criteria-split-now-and-later`; an edited
  mockup and four bullets score 9/9. The accessibility skill's defining
  promise (drives the artifact: tab order, computed contrast) is
  structurally untestable with the case's tools, and only the payfine case
  checks the fallback is admitted.
- `screen-design-payfine`: every grader reads `screen-design-001.md`; no
  grader opens a mockup, so token reuse (the skill's central promise) is
  judged from prose. `design-system-payfine-phase2` judges candidate
  distinctness from prose for the same reason.
- `architecture-design-payfine-phase1` judges "waits without writing the
  design" from the message while `Write` is allowed and no grader checks
  the file system.
- `operational-readiness-*-phase1`: the skill mandates asking whether a
  rollback has ever been run; the grader says it "is a plus, not
  required". Phase 2 then supplies the answer in the prompt.

## 8. Coverage gaps worth closing first

Promises in a skill that no grader anywhere checks, limited to the ones
that affect correctness of the autonomous path:

- tdd-implementation: right-reason RED, full-suite after GREEN, REFACTOR,
  Critical/High fix-and-re-run, revert of an earlier design edit,
  escalation naming the owning skill, quarantine flow.
- orchestrator: log entry content, save location passed to the routed
  skill, not answering the routed skill's questions, not chaining
  silently.
- code-review: the mandated `why-comments` consult.
- security-requirements and reliability-requirements: the stop-and-report
  path when a slice can't be made safe without unscoped capability; the
  ADR hand-off; all five data exits (the grader needs two).
- vertical-slicing: the mandated `acceptance-criteria` consult; the
  "Explicitly deferred" and "Still open" sections; a run that correctly
  stops to ask fails every file grader.
- adr: the three-part worthiness test is never graded.
- design-system: reference-match path and review/evolve mode have no case.

## Recommended order

1. **Fix the gate's arithmetic.** Re-record bars from gate-mode runs,
   lower tolerance or make it per-grader, gate the two ungated cases,
   delete the `Task` graders and re-record the two via-agent bars.
2. **Build the validation gate out of the tdd cases.** Replace the
   ordering and self-report graders with trace proofs (a red run after
   each test write, green at the end, a deliberate-break red followed by
   green), add a Bash-write guard, anchor the whole design doc, add
   `--test-reporter=spec`. These same checks are the mechanical floor the
   orchestrator's Grade step needs, so this work is not eval-only.
3. **Move long reports to files.** Apply the `days-left-pr` pattern to
   every review case; drop `last_message` except for phase-1 questions.
4. **Re-freeze the phase chains** from current skill text, stopping
   phase 2 at the fork with no criteria written, and add one chain whose
   answer rejects the recommendation.
5. **Strip the leaks.** Change the two skill worked examples or the two
   prompts that copy them, cut the hint sentences from four prompts,
   remove the persona names from three fixtures, drop the staleness
   sentence from `map-query-consults`.
6. **Give the routing cases one outcome grader each** on the log entry
   and one on the final message, and the restraint cases a positive
   grader naming what holds the module up.
7. Only then widen the suite toward judgment (rejecting answers, harder
   plants) so scores can move off the 1.0 ceiling and the lite-versus-heavy
   comparison has something to measure.
